# Problem Statement 3 Briefing Notes: On-Device Threat, Phishing, and Scam Detection

Speakers: Arm challenge representative (opening, 00:00-01:37); Dr. Vijay Kumar, IIT Delhi (PS3 walkthrough, 01:47-11:29). Cleaned transcript: docs/ps3_transcript.md.

## Summary
The Bharat AI-SoC Challenge (Edition 2, 2026-27) Problem Statement 3 briefs participants on constructing an edge-native digital safety assistant running on Arm hardware.
The system covers three threat channels: network traffic anomalies, phishing URLs, and scam SMS messages, providing plain-language explanations and remediation guidance.
A strict architectural rule separates detection from explanation: specialist classifiers/heuristics perform threat scoring, while an on-device Llama model via ExecuTorch provides bounded advisory explanations.
Inference must run entirely offline without internet dependencies, preserving user privacy and ensuring low latency.
Teams can optionally accelerate compatible detectors on a Hailo NPU via HailoRT while executing Llama on the Arm CPU.
Participants are advised to select one focused use case for an end-to-end prototype while maintaining an extensible pipeline.
Evaluation benchmarks detection quality (precision, recall, FPR, latency), on-device efficiency (inference time, RAM, CPU/NPU load), and user comprehension.

## Requirements and evaluation hints
* **Mandatory On-Device Execution [03:46, 06:16]**: The entire pipeline must execute locally on Arm-based hardware without network dependencies. Speaker quote: "The key requirement is that the system must run locally on ARM-based hardware and continue working without an Internet connection."
* **Mandatory Llama + ExecuTorch Stack [05:32, 06:16]**: Reasoning and user-facing explanations must be generated by a Llama family model running via the ExecuTorch runtime on the Arm CPU. Speaker quote: "Use the LAMA family model to reasoning and the XU torch to run it locally on the device."
* **Strict Detector vs. LLM Separation ("Important Design Rule") [04:58 - 05:48]**: Llama must not be used as a raw signal classifier. Specialist ML models or rules must generate structured detection outputs (label, numerical score, threat indicators), and Llama consumes this structured evidence to generate short, bounded explanations and remediation steps. Speaker quote: "The key point is that the specialist model detect the threat while the language model explain them and recommended action. This makes the system more efficient and easier for the user to understand."
* **Heterogeneous Acceleration Guidelines (Hailo NPU) [06:23 - 06:40]**: If using a Hailo AI HAT, HailoRT is restricted to compatible detector/classifier workloads on the NPU, while Llama remains on the Arm CPU under ExecuTorch. Both inference pipelines must remain architecturally decoupled.
* **Safety and Autonomy Bounds [07:34 - 08:07]**: The assistant must not execute destructive autonomous actions. Slide rule: "Never auto-click, auto-delete, or claim certainty from the LLM alone." Speaker quote: "The system should never automatically click the link or claim that its predictions are always correct." Human-in-the-loop decision support is required.
* **Single Focused Use Case Recommendation [07:05 - 07:29]**: Teams are instructed not to build all three threat channels simultaneously for Phase 1. Speaker quote: "Do not try to build everything at once. Focus on one working solution, you can choose one of the three options... Choose one main use case and make it [run] properly. Keep the code modular so you can add other features later."
* **Three-Pillar Evaluation Criteria [08:14 - 09:04]**:
  - *Detection Quality*: Precision, recall, false-positive rate, and detection latency across threat categories. Speaker quote: "how accurately does the device or your system detect the threat and how often does it raise the false alarm."
  - *On-Device Performance*: Execution latency, RAM usage, CPU/NPU utilization, thermal profile, and verification of zero internet reliance. Speaker quote: "how quickly the response and how much memory does it use while running offline."
  - *User Effectiveness*: Comprehensibility of generated explanations, clarity of risk communication, and user action completion rate. Speaker quote: "can ordinary users understand the explanation and follow the recommended example."
* **Four Official Submission Deliverables [10:03 - 10:43]**:
  1. *Source Code*: GitHub repository with automated step-by-step installation scripts.
  2. *On-Device App*: Standalone compiled binary (Android APK, Linux wheel, or native binary executable).
  3. *Demonstration Video*: Live technical walkthrough demonstrating real threat triggers on physical hardware with no network connection.
  4. *Engineering Report*: Rigorous document covering hardware mapping, quantization configurations, architectural design, and measured KPIs.
